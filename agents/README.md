# AutoSRE Agent

## Autonomous SRE Investigation and Remediation Engine

AutoSRE is a safety-first, event-driven incident response system. It detects reliability anomalies, investigates root causes, proposes remediation, enforces deterministic safety policies, obtains human approval when required, executes allowlisted actions, and verifies the results.

### Design Principles
1. **Detection is separate from reasoning.** OpenObserve detects; AutoSRE reasons.
2. **Reasoning is separate from execution.** LLMs propose; `SafeExecutor` executes.
3. **Deterministic safety boundary.** No LLM has unrestricted infrastructure access. Every mutation is policy-gated.
4. **Durable, resumable state.** PostgreSQL-backed LangGraph persistence survives process crashes and Human-in-the-Loop (HITL) pauses.
5. **Verification over assumption.** Tool success ≠ incident resolution. State changes are explicitly verified.

## 2. System Architecture

```text
[Applications] --(logs/metrics)--> [OpenObserve] --(alert webhook)--> [AutoSRE Agent (FastAPI)]
                                                                        |
                                                                        v
                                                           [LangGraph State Machine]
                                                                        |
                                            +---------------------------+---------------------------+
                                            |                           |                           |
                                            v                           v                           v
                                  [Kubernetes Tools]          [PostgreSQL Tools]          [Valkey Tools]
```

**Responsibilities:**
- **OpenObserve:** Ingests telemetry, evaluates alert rules, maintains alert state, and delivers HTTP webhook notifications.
- **AutoSRE:** Deduplicates webhooks, gathers evidence via typed tools, identifies root causes, enforces safety policy, manages HITL, executes allowlisted mutations, and verifies outcomes.

## 3. LangGraph Orchestration (The Core DAG)

The agent is not an unconstrained LLM loop. It is an explicit, cyclic, stateful Directed Acyclic Graph (DAG) implemented via LangGraph. The graph persists its state (`AgentState`) to PostgreSQL, allowing it to pause for human approval or survive process restarts without losing context.

### 3.1 State Schema (`AgentState`)
The graph passes a single mutable state dictionary between nodes:
- `hypotheses`: List of root-cause explanations with confidence scores and attached evidence.
- `proposed_actions`: The concrete remediation step(s) generated by the LLM or fallback logic.
- `executed_actions`: History of tools actually dispatched via `SafeExecutor`.
- `current_phase`: Tracks graph position (`triage`, `investigate`, `hypothesize`, `propose`, `approve`, `execute`, `verify`, `complete`).
- `iteration_budget` / `stagnation_count`: Controls the investigate/hypothesize loop to prevent infinite LLM spinning.
- `approval_granted`: Boolean flag set after HITL interrupt resolves.

### 3.2 Node Responsibilities & Routing Logic

1. **`triage`**
   Normalizes the incoming alert.
   *Routing:* If the incident category is a known no-action type (e.g., `webhook_dedup`, `prohibited_action`), it **early-exits** directly to `complete` with `status="no_action"`, saving 100+ seconds of LLM calls. Otherwise, routes to `investigate`.

2. **`investigate`**
   Gathers evidence using Tier-0 (read-only) tools.
   *LLM-Resilience:* If the LLM tool-selection call fails (budget/quota), the node deterministically falls back to executing *all* available Tier-0 tools with sensible default arguments derived from incident metadata. Routes to `hypothesize`.

3. **`hypothesize`**
   Refines hypothesis confidence based on new evidence.
   *Routing (`route_after_hypothesize`):*
   - If `top_confidence >= threshold` → route to `propose`.
   - If `iteration_budget <= 0` OR `stagnation_count >= 2` → route to `propose` (triggers fallback logic).
   - Otherwise → loop back to `investigate`.

4. **`propose`**
   Converts the top hypothesis into a concrete remediation action.
   *Safety Gates:*
   - Checks if the LLM-proposed tool is in `_CATEGORY_FORBIDDEN_TOOLS`. If so, rejects it and forces the fallback path.
   - If LLM confidence is low or it returns `"none"`, it deterministically selects the action from `FALLBACK_ACTIONS[category]`.
   - Validates that the proposed arguments satisfy the tool's Pydantic `input_model` schema before proceeding.
   *Routing:* If `risk_tier >= 2`, routes to `approve`. Else, routes to `execute`.

5. **`approve`**
   Manages Human-in-the-Loop.
   *Mechanism:* Uses LangGraph's `interrupt()` primitive. On first entry, it records `approval_requested_at` and pauses the graph, persisting state to PostgreSQL. When the external API (`POST /incidents/{id}/approve`) is called, the graph resumes, the interrupt returns the decision, and `approval_granted` is set.
   *Routing:* If approved, routes to `execute`. If denied, routes to `complete` with `status="no_action"`.

6. **`execute`**
   Dispatches the action to the `SafeExecutor`.
   *Crucial Detail:* If `approval_granted == True`, it explicitly downgrades the action's `risk_tier` to 1 and `requires_approval` to `False` before handing it to the executor. This prevents the executor's internal policy engine from re-triggering the HITL gate for an action the graph has already cleared.
   *Routing:* On success, routes to `verify`. On failure, routes back to `propose` (if attempts < max).

7. **`verify`**
   Checks the `verification_passed` flag from the executed tool.
   *Routing:* If `True` → `complete` (`status="resolved"`). If `False` and `action_attempts < max` → loop back to `propose` to try an alternative. If max attempts reached → `complete` (`status=" ailed"`).

8. **`complete`**
   Terminal node. Computes final metrics (wall-clock time, active time, LLM latency, cost), derives the final status, and halts the graph.

## 4. Safety & Execution Layer

The safety layer is the absolute control boundary between LLM reasoning and infrastructure mutation.

### 4.1 Risk Tiers
| Tier | Meaning | Execution |
|------|---------|-----------|
| 0 | Read-only / diagnostic | Autonomous |
| 1 | Low-risk operational remediation | Autonomous |
| 5.2 | Potentially disruptive remediation | HITL required |
| 3 | High-impact remediation | HITL required and restricted |
| 4 | Prohibited action | Hard blocked |

### 4.2 SafeExecutor
No infrastructure mutation bypasses `SafeExecutor`. Its pipeline is strictly linear:
1. **Risk Classification:** `effective_tier = max(registered_tier, proposed_tier)`. The LLM cannot downgrade a tool's inherent risk.
2. **Policy Decision:** Evaluates against allowlists/denylists.
3. **HITL Gate:** Raises `NeedsApprovalError` if `decision.requires_approval == True`.
4. **Snapshot:** Captures pre-state for potential rollback.
5. **Execution:** Invokes the allowlisted tool handler.
6. **Verification:** Checks resulting state.
7. **Rollback:** Triggered automatically if execution or verification fails and a rollback handler is registered.

### 4.3 Category-Forbidden Tools
To prevent plausible-but-dangerous LLM hallucinations, specific tools are hard-blocked per incident category, regardless of LLM confidence.

```python
_CATEGORY_FORBIDDEN_TOOLS = {
    "cache_eviction": {"restart_deployment"},
    "db_connection_exhaustion": {"restart_deployment"},
    "cpu_saturation": {"restart_deployment", "delete_pod"},
    "pod_oom": {"scale_deployment"},
    "memory_pressure": {"scale_deployment"},
}
```
The `propose_node` enforces this check in three places: after the primary LLM proposal, after Fallback Path 1 (low confidence), and after Fallback Path 2 (LLM returned "none").

## 5. Tool Registry

Tools are explicitly registered, strictly typed via Pydantic, and scoped to narrow operations. No arbitrary shell execution is exposed.

- **Kubernetes (`k8s.py`):** Pod/deployment inspection, metrics, `restart_deployment`, `delete_pod` (force), `scale_deployment`.
- **PostgreSQL (`postgres.py`):** Connection stats, active queries, safe `terminate_backend` (refuses superuser/self connections).
- **Valkey (`valkey.py`):** Cache stats, stream info, targeted `delete_valkey_key`, and Tier-2 `flush_all`.
- **OpenObserve (`observability.py`):** Bounded SQL-compatible log/metric queries for evidence gathering.

## 6. Optimization: Routing & Context

### 6.1 Token-Velocity Model Routing
`src/autosre/core/router.py` dynamically selects between a fast, cheap worker model and a heavy-context coordinator model based on the estimated token size of the accumulated investigation state. This prevents unnecessary cost and latency on simple incidents while preserving capacity for complex root-cause analysis.

### 6.2 Context Eviction
Infrastructure tools can return massive payloads (e.g., full pod logs). The context eviction middleware compacts oversized tool outputs into smaller, evidence-preserving representations (e.g., extracting error signatures, timestamps, and counts) before they are fed back into the LLM, preventing context window exhaustion and reducing token costs.

## 7. Webhook Ingress & Durable State

### 7.1 Ingress Pipeline (`POST /alerts`)
1. **Authenticate/Validate:** HMAC-SHA256 verification (in production) and Pydantic schema validation.
2. **Deduplicate:** Agent-side deduplication protects against OpenObserve retry storms or duplicate webhook deliveries.
3. **Resume/Create:** Loads existing incident state from PostgreSQL or initializes a new `AgentState`.
4. **Invoke Graph:** Streams the state into the LangGraph entry point.

### 7.2 Durable State
LangGraph is configured with an `AsyncPostgresSaver`. If the agent pod crashes mid-investigation or pauses indefinitely at the `approve` node, a restart will load the exact graph state, node position, and iteration counts from the database, resuming seamlessly without re-executing prior side effects.

## 8. Deployment & Integration (Condensed)

### 8.1 Ownership Boundaries
- **OpenObserve Deployment Script:** Provisions the required data streams (`app_logs`, `postgres_logs`, `valkey_logs`, `app_metrics`).
- **Terraform/OpenTofu:** Provisions alert folders, templates, webhook destinations, and the 14 alert rules. *Terraform does not manage streams* to avoid provider/server version mismatches.

### 8.2 Network Trust
In local Kind staging, OpenObserve is configured with `ZO_SKIP_SSRF_CHECKS=true` to allow webhooks to `http://autosre-agent.sre.svc.cluster.local:8000/alerts`. In production, this SSRF bypass should be replaced with proper network egress controls and an externally reachable HTTPS destination with strict HMAC signing.

### 8.3 Deployment Order
1. Deploy Kubernetes/Kind cluster.
2. Deploy OpenObserve and provision streams.
3. Deploy AutoSRE agent (with PostgreSQL persistence).
4. Apply Terraform alerting configuration.
5. Trigger chaos incident to verify end-to-end flow.
